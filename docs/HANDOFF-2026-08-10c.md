### The non-obvious things a future session would break

1. **The code writes 18 `entry_type` values, not the 8 the live data shows.** `crop_sale`,
   `cane_sale`, `livestock_sale`, `residual_sale`, `tree_sale`, `revenue_receipt`,
   `owner_capital`, `opening_cash`, `transfer`, `vendor_payment`, `labour_payment`,
   `salary_payment`, `advance_payment`, `expense_payment`, `owner_drawing`,
   `commission_expense`, `freight_expense`, `sale_deduction`. All are classified. Test 1
   fails if a nineteenth appears — that is deliberate, it is how the table stays honest.

2. **`opening_cash` is excluded from the three sections and added as opening instead.**
   Under the All Time filter those rows fall *inside* the period, so if they were merely
   dropped, closing cash would be short by exactly the opening balances. `buildCashFlow`
   adds `openingCash` (carried in from before the period) **plus** any in-period
   `opening_cash` rows. Do not "simplify" this to one source. It has a test.

3. **`tree_sale` splits on its notes prefix**, because one entry_type covers a fruit lease
   (farming income → Operating) and felling a tree (asset disposal → Investing). The
   prefix is a shared constant so writer and reader cannot drift. Do not inline the string
   back into `trees.js`.

4. **Investing outflow reads ₹0 on purpose, with an explanation and a memo box.** A payment
   settles the party, not the bill, so the cash for Ankur's ₹5,000 sprayer cannot be told
   apart from the cash for his seed. Apportioning vendor payments across bill lines was
   **explicitly rejected** — it would look precise and not be true. Do not "fix" this by
   splitting payments; it is the settled architecture, not a defect.

5. **`vitest.config.js` is deliberately separate from `vite.config.js`** so a test setting
   can never break a Vercel deploy. Keep it that way.
